## Findings

### P1 — G0 release and program evidence remain open

Evidence: the public repository, protected default branch and [successful
default-branch CI run](https://github.com/daichunghy/patchgate/actions/runs/32333914059),
public Project #1, five Discussions, four open contribution/pilot issues and
PR #9 are observable. `package.json` remains private; there is no release,
merged PR, downstream usage or completed pilot evidence.

Impact: the repository can truthfully be described as a public pre-release
open-source project, but not as a released or adopted product and not as an
eligible/selected Codex for Open Source project. The application dossier must
remain preparation-only.

Required evidence: maintainer role confirmation, working public
support/security routes, a release/rollback decision, and later usage or pilot
evidence.

### P2 — community activity is supporting evidence, not adoption

The public Project, five self-authored Discussions, issue start paths and four
context-specific outbound questions show organized maintenance and ecosystem
research. They do not show independent community participation because no
external reply, contribution or pilot has been recorded yet. Keep these links
in the dossier as maintenance context, not as usage metrics.

### P1 — G4 is PR/clean-room evidence, not shadow completion

The Action bundle now starts in a clean room without source schemas or
`node_modules`; check delivery updates an existing check by `head_sha` and
`check_name`; the consumer fixture verifies a full-SHA reference and clean-room
bundle; and `merge_group` returns explicit `evidence_missing` rather than
silently passing. These are local/fixture controls only.

Missing: a live external consumer repository, fork E2E, live merge-group E2E,
two consenting non-blocking shadow installations, public immutable Action tag
and maintainer review of observed distribution/noise.

On the current PR, the non-required Shadow Gate still fails at the expected
trusted-base transition boundary: `pull_request_target` executes the workflow
and local Action metadata from `main@a3745f6`, whose workflow still passes the
empty `secrets.GITHUB_TOKEN`. PR #9 changes this to the repository-scoped
`github.token`; the corrected shadow run can only be observed after the
workflow change is merged. This failure is retained as evidence of the
transition, not bypassed or counted as a passing shadow installation.

## Live continuation update — 2026-08-22

PR #9 remains open and requires an independent approval; required CI, CodeQL and
security checks are passing, while the non-required Shadow Gate still fails at
the documented trusted-base transition boundary. The first scheduled prompt was
backfilled manually as [Discussion #10](https://github.com/daichunghy/patchgate/discussions/10)
using the prepared Q&A copy. It has no comments or external participation yet.
The remaining six prompts are now scheduled for 2026-08-24, 08-26, 08-28,
08-30, 09-01 and 09-03; the repository-scoped workflow remains inactive until
the PR is merged.
The application pack now records the live 0-star/0-fork/no-release state and
validates all three official form text fields against the 500-character limit;
applicant identity and Organization ID remain manual inputs.
Live branch protection was then read back with six strict required CI contexts,
including `CI / Full Verify`, while the one approving-review requirement and
stale-review dismissal remained unchanged. This makes the full verification
surface part of the merge gate rather than a local-only or advisory check.
The CI definition now also runs the complete `npm run verify` chain in a
dedicated Full Verify job, covering the application validator, community
schedule, consumer fixture, release-candidate check and clean-room bundle in
GitHub Actions rather than only on the local checkout.
The first Full Verify run exposed an Action-entrypoint isolation bug: importing
`src/action/index.ts` while `GITHUB_ACTIONS=true` triggered the production
runner during Vitest and caused an unhandled `process.exit(2)`. The runner now
auto-starts only for the bundled `dist/action/index.js` entrypoint; the exact
CI environment is covered by `GITHUB_ACTIONS=true npm run verify` locally and
the subsequent GitHub rerun.
That rerun then exposed a second clean-checkout ordering defect: the release
candidate check expected `dist/src/cli.js` before the verification chain had
built the CLI. The chain now runs `npm run build` before bundling and release
candidate validation, so a fresh CI checkout no longer depends on stale local
`dist` output.
The next CodeQL pass identified a high-severity URL-substring validation in the
new application-dossier checker. The checker now matches the complete official
form line rather than accepting an arbitrary URL containing the expected text.
